## U-20261008-01 · 2026-10-08 · Workflows are validated without running: schema, lint rules, CLI · #done #feature #validation

- **What**: phase 1 of the platform roadmap (PR #32, `docs/roadmap-platform-improvements.md`). Until now the only way to find a mistake in a workflow was to execute it and read the log.
  - **Schema**: `test_pioneer/schema/spec.py` describes the workflow once: top-level keys, the nine step types in dispatch order, and each one's fields. `definition.py` builds the JSON Schema (draft 2020-12, `version` 1.0.0) from it; `schema/testpioneer.schema.json` is that schema written to disk for editors.
  - **Loader**: `load_yaml` parses with `yaml.SafeLoader` and records the line and column of every key and value. Syntax errors, unreadable files and duplicate keys come back as diagnostics. A node reached through several aliases is indexed once, so nested aliases cannot make the walk grow without bound.
  - **Schema check**: `validate_yaml`. A built-in validator covers the nine keywords the schema uses, so `test_pioneer` gains no dependency.
  - **Lint rules**: `lint_yaml` adds what a schema cannot say: duplicate step names, a step with no action or with several, a field an action needs, `runners`/`scripts` of different lengths (errors); unknown keys with the closest known key suggested, fields of another action, `close_program` without an open program, a runner package that is not installed, a script or folder that does not exist (warnings).
  - **CLI**: `python -m test_pioneer validate <files> [--format {text,json}] [--strict] [--base_dir DIR] [--no_file_check]` exits 1 on an error; `python -m test_pioneer schema [-o FILE]` prints the schema. `-e/--execute_yaml` is unchanged, and `execute_yaml` does not call the validator, so every workflow runs as it did.
  - **Models**: `test_pioneer/models/`: `Diagnostic` and `ValidationResult`, plus the normalized run result (`RunResult`, `StepResult`, `RunnerResult`, `Artifact`, `Status`) that phases 2 and 3 fill in.
  - `test_pioneer/runner/registry.py` now holds the runner-to-package table that `parallel_run` kept privately; the schema's runner enum and the linter read the same table.
- **Result / numbers**:
  - 153 new tests in six files; suite 276 passed, with `test_run_folder_files.py::test_run_folder_with_a_real_runner_executes_every_file` not run on this machine (it needs the runner packages, whose install had not finished).
  - The built-in validator and `jsonschema` 4 (`Draft202012Validator`) reject the same paths in all 785 generated documents of the cross-check; a 465-document version of that check is in `test/test_schema_validator.py` and runs wherever `jsonschema` is installed, which CI's unit-test job now does.
  - `mypy --strict`, `ruff`, `bandit` and `pylint` report nothing for the new modules.
  - Run over the repository's own samples, `validate` found the problems recorded as `progress.md` #11.
- **Guards**: `test/test_schema.py` fails when the published schema differs from the built one, when the schema uses a keyword the validator does not implement, and when `ACTIONS` and the executor's `_STEP_HANDLERS` differ in content or order.

## U-20261008-02 · 2026-10-08 · Runs have an ID, a result and kept failure artifacts · #done #feature #artifacts

- **What** (`progress.md` #7, phase 2 of the platform roadmap, PR #32): `parallel_run` started its runners and waited, and nothing recorded how they ended; a runner that failed left no trace and did not change the outcome.
  - **Run**: `execute_yaml` opens a `RunSession` with a run ID (`20261008T031542Z-9f2c1a7b`, or the caller's) and returns a `RunResult`: every step and every runner execution with its status, timing and message. It used to return `None`.
  - **Artifacts**: `<artifacts_path>/<run-id>/runners/<runner>/<nn>-<step>/` per runner execution and `testpioneer/{execution.log,manifest.json}`. `keep_artifacts` is `on_failure` (default: a run that passed leaves nothing, a failed one keeps what did not pass), `always` or `never`. Both are new optional top-level YAML keys and `RunOptions` fields.
  - **Runner contract**: each runner execution gets `TEST_PIONEER_RUN_ID` and `TEST_PIONEER_ARTIFACT_DIR`. A runner that ignores them is wrapped: a sub-process writes to `stdout.log` / `stderr.log` (copied to the console from the wait loop) and its exit code is recorded; an in-process call has `sys.stdout` / `sys.stderr` copied to the same files. No thread is used, because screen recording replaces `threading` with greenlets.
  - **Adapter**: `runner/adapter.py` defines `RunnerAdapter` and `ModuleRunner`; `RUNNERS` in `runner/registry.py` replaces the plain name-to-package table.
  - **CLI**: `python -m test_pioneer run <file> [--run_id] [--artifacts_path] [--keep_artifacts]` exits 1 when the run did not pass. `-e` still exits 0 whatever the steps did.
  - Step messages reach the run's `execution.log` through a sink in `step_log_check`, so the `TestPioneer` logger stays silent unless `pioneer_log` is set, as before.
- **Compatibility**: a failed `parallel_run` runner still does not stop later steps; it now makes the step and the run `failed`. Exceptions propagate as before, after the run is recorded as `error`. A handler called outside `execute_yaml` finds no session and starts its process exactly as before. An `OSError` while collecting artifacts becomes a warning on the result.
- **Found while here**: all five runner packages exit 0 when an action of a script fails and none reads an artifact directory from the environment (`architecture.md` §6, `progress.md` #13), so an exit code marks a run `failed` only for a missing or malformed script. `process_manager_instance.name_set` is never emptied between calls (`progress.md` #12).
- **Result / numbers**: 102 new tests (`test_artifacts.py` 58, `test_run_session.py` 26, `test_parallel_run_artifacts.py` 12, `test_cli.py` +6); suite 378 passed. The `parallel_run` tests start real sub-processes of a stand-in runner package: one passes and one exits 3, a missing script, an unknown runner, a Python that does not exist, and an interrupted wait. `mypy --strict`, `ruff` and `pylint` report nothing for the new modules.
